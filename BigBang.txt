## Objective

Build a **minimal, fast, cross-platform Local Work Reporting MVP** for a software development team.

The application is a completely local desktop application. Each developer installs and runs the application on their own computer.

There is **no central backend, database, API, or application server**.

The primary goal is to reach a usable MVP with the **smallest reasonable amount of code and the shortest possible development time**.

Do not over-engineer the solution.

---

# Technology Stack

Use the following technology stack:

* **Language:** Java 21 LTS
* **Desktop UI:** JavaFX
* **Build Tool:** Maven
* **Git Integration:** Native Git CLI through Java `ProcessBuilder`
* **Data Storage:** Plain `.txt` files
* **Database:** None
* **Backend:** None
* **Networking:** None, except Git operations
* **Packaging:** `jpackage`

The application must be able to run on:

* Windows
* Linux
* macOS

### Why this stack?

The project is intentionally simple and local-first.

Java + JavaFX provides:

* Cross-platform desktop support.
* A mature ecosystem.
* A single programming language for the entire application.
* No need for a backend.
* No need for a database.
* No need for Electron/Node.js.
* Straightforward filesystem access.
* Straightforward process execution for Git.
* Simple packaging using `jpackage`.

Do not introduce additional frameworks unless there is a strong technical reason.

Avoid unnecessary dependencies.

---

# Core Concept

The application manages work reports stored as `.txt` files inside a Git repository.

Git acts as the **transport and synchronization mechanism** between developers.

The application itself does not need any remote server.

The architecture should essentially be:

```text
JavaFX UI
    │
    ├── ReportService
    │       └── Local .txt files
    │
    └── GitService
            └── Git CLI
```

The filesystem is the source of truth.

Git is only responsible for synchronizing those files between developers.

---

# Core Features

The MVP must support exactly these core operations:

## 1. Create

A developer can create a new work report.

The report is saved as a `.txt` file inside a predefined reports directory in the selected project.

Example:

```text
project/
└── reports/
    ├── 2026-08-14-alice.txt
    └── 2026-08-14-bob.txt
```

The report should contain simple structured information such as:

```text
Date: 2026-08-14
Developer: Alice
Start Time: 09:00
End Time: 12:30

Summary:
Implemented the authentication module.

Tasks:
- Implemented login flow.
- Added JWT validation.
- Fixed authentication middleware.

Notes:
Authentication tests were added and verified.
```

Keep the format simple, deterministic, human-readable, and Git-diff-friendly.

---

# 2. View

Display all available local reports.

The application should scan the reports directory and parse the `.txt` files.

The main UI should provide a simple list/table containing information such as:

* Date
* Developer
* Start time
* End time
* Short summary

Selecting a report should display its complete contents.

---

# 3. Edit

A developer can edit an existing report.

Saving the report must modify the corresponding `.txt` file.

Do not introduce a database or caching layer.

---

# 4. Delete

A developer can delete a report.

Show a confirmation dialog before deletion.

Deleting the report should simply delete its `.txt` file.

Git will then recognize the deletion as a normal repository change.

---

# Git Integration

Git integration should remain intentionally simple.

Use the installed Git executable through Java's `ProcessBuilder`.

Do not implement a full Git client.

The MVP should support:

* Detecting whether the selected project is a Git repository.
* Checking Git status.
* Running `git pull`.
* Running `git add`.
* Running `git commit`.
* Running `git push`.

The application should provide simple UI actions such as:

```text
[ Pull ]    [ Save ]    [ Commit & Push ]
```

Do not build advanced Git functionality unless it is required for the MVP.

---

# Git Synchronization Workflow

The expected workflow is:

```text
Developer A
     │
     │ Create/Edit report
     ▼
Local .txt file
     │
     │ Commit & Push
     ▼
Remote Git Repository
     │
     │ Git Pull
     ▼
Developer B
     │
     ▼
Local .txt file
     │
     ▼
Report appears in application
```

After `git pull`, the application should refresh the reports directory and display newly synchronized reports.

The application must not require a remote API or backend.

---

# Project Selection

On first launch, allow the user to select the local project directory.

The application should:

1. Check whether the directory is a Git repository.
2. Locate the reports directory.
3. Create the reports directory if it does not exist.
4. Scan existing `.txt` reports.
5. Display them.

Remember the selected project path for subsequent launches.

Keep configuration minimal.

A simple local configuration file is sufficient.

# Local-First Requirements

The application must work without an internet connection.

The following operations must work completely offline:

* Create report.
* View report.
* Edit report.
* Delete report.
* Search reports.
* Browse reports.

Only Git synchronization requires network connectivity.

There must be no dependency on:

* Cloud services.
* Remote APIs.
* Databases.
* Authentication.
* Backend services.

---

# Error Handling

Handle the most important failure cases gracefully:

* Git is not installed.
* Selected directory is not a Git repository.
* Reports directory does not exist.
* Report file is malformed.
* File cannot be read.
* File cannot be written.
* File is deleted externally.
* `git pull` fails.
* `git push` fails.
* Git reports a merge conflict.

Do not silently lose data.

For the MVP, error handling should be simple and understandable.

Avoid building an elaborate recovery system.

---

# Git Conflicts

Do not attempt to automatically resolve Git merge conflicts.

If `git pull` produces a conflict:

1. Detect the failure.
2. Display a clear error message.
3. Do not overwrite files.
4. Tell the user that the Git conflict must be resolved.
5. Allow the user to continue using the application after the conflict is resolved.

# Architecture

Keep the architecture intentionally small.

Suggested structure:

```text
src/main/java/
└── com.example.workreport/
    ├── Main.java
    ├── ui/
    │   └── MainView.java
    ├── model/
    │   └── WorkReport.java
    ├── service/
    │   ├── ReportService.java
    │   └── GitService.java
    └── util/
        └── AppConfig.java
```

This structure is only a guideline.

Do not create excessive abstractions, interfaces, factories, repositories, dependency injection layers, or enterprise architecture.

For this MVP, **simple code is better than architectural complexity**.

---

# ReportService

`ReportService` should be responsible for:

* Creating reports.
* Reading reports.
* Updating reports.
* Deleting reports.
* Searching reports.
* Parsing `.txt` files.
* Serializing `WorkReport` objects to `.txt`.

It should work directly with the filesystem.

It must not depend on Git.

---

# GitService

`GitService` should be responsible for:

* Checking Git availability.
* Checking repository status.
* Running `git pull`.
* Running `git add`.
* Running `git commit`.
* Running `git push`.

Use `ProcessBuilder`.

Keep the implementation small and transparent.

Do not introduce JGit unless there is a compelling reason that the Git CLI approach cannot satisfy the MVP requirements.

---

# Important Principle: No Database

Do **not** use:

* SQLite
* PostgreSQL
* MySQL
* H2
* MongoDB
* Redis

The `.txt` files are the database.

This is intentional.

The application should always be able to reconstruct its state simply by scanning the reports directory.

---

# Important Principle: No Backend

Do not create:

* Spring Boot
* REST API
* WebSocket server
* Node.js backend
* Python backend
* Docker services

This is a desktop application, not a web application.

---

# Packaging

The final application should be packaged as a standalone desktop application.

Use Java's `jpackage`.

The goal is to provide platform-specific packages such as:

```text
Windows → .msi / .exe
Linux   → .deb / appropriate package
macOS   → .dmg
```

The end user should not need to manually configure a Java runtime if the application is packaged with its required runtime.

The only external requirement should be **Git**, because Git is part of the synchronization mechanism.

---

# Development Priorities

Follow this priority order:

1. Working application.
2. Create/View/Edit/Delete reports.
3. Reliable `.txt` storage.
4. Git Pull.
5. Git Commit & Push.
6. Basic search/filtering.
7. Error handling.
8. Packaging.
9. UI polish.

Do not spend significant time on features that do not directly contribute to the MVP.

---

# Explicitly Avoid

Do not add the following unless absolutely necessary:

* User accounts.
* Authentication.
* Cloud storage.
* Database.
* Backend.
* REST APIs.
* Docker.
* Microservices.
* Complex dependency injection.
* Advanced Git UI.
* Advanced permissions.
* Notifications.
* Analytics.
* Complex configuration.
* Enterprise architecture.
* Plugin systems.

The objective is a **small desktop utility**, not a full project-management platform.

# Definition of Done

The MVP is complete when a developer can:

1. Install the application.
2. Select a local Git project.
3. Open the application.
4. See existing work reports.
5. Create a new report.
6. Edit a report.
7. Delete a report.
8. Pull reports created by other developers.
9. See synchronized reports immediately after pulling.
10. Commit and push report changes.
11. Continue using the application without internet access.
12. Run the application on Windows, Linux, and macOS.

The final implementation should favor **the smallest amount of code that reliably satisfies these requirements**.

When there are multiple technically valid approaches, choose the one with:

**less code → fewer dependencies → simpler deployment → easier maintenance.**

Do not optimize for architectural sophistication. Optimize for **shipping the MVP as quickly as possible**.
